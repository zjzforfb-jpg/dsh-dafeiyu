# 大肥鱼项目缺陷治理与稳定化计划

版本：1.0 · 2026-11-14

本文是大肥鱼当前阶段的缺陷修复基线。它把“功能存在”“一次运行成功”和“可以长期稳定使用”分开，并规定每个问题必须经过发现、复现、定位、修复、验证、实机观察和关闭，避免修完一次后再次回归。

## 1. 当前产品判断

大肥鱼目前是一个由桌宠、DeepSeek 脑服务、SQLite 记忆、Mac 常驻服务、Android Companion、微信 iLink、QQ 机器人、语音链路和 ADB/macOS UI 自动化组成的个人实验型 Agent。

已经有真实闭环的能力包括：桌面悬浮、基础文字对话、长期记忆、日记与探索、Mac 常驻、Magic5 设备在线、微信 iLink 文字、微信语音转写、M4A 音频回复、QQ 文字/语音消息，以及部分抖音自动化。

尚不能统一称为稳定产品能力的包括：群聊外部动作、抖音点赞、抖音长期互动守护、原生微信语音气泡、电话音频桥、跨渠道统一人格、跨渠道统一记忆、发布审批、Android 跨 App 操作和多平台运营。

当前的核心风险不是“功能数量不足”，而是多个入口各自拥有提示词、记忆、动作和状态，导致模型口头答应但任务未创建、任务执行但没有真实回执、群友可以影响外部动作、文档与生产配置不一致，以及服务重启后无法确定外部动作是否已经发生。

## 2. 缺陷分类

每个缺陷必须至少归入一个类别：

| 类别 | 定义 | 典型例子 |
| --- | --- | --- |
| 功能缺陷 | 代码路径没有实现或实现结果错误 | 点赞动作未实现却被描述为可用 |
| 状态缺陷 | 状态没有准确反映真实结果 | 模型说“已完成”，设备没有回执 |
| 逻辑缺陷 | 条件、权限、上下文或状态转换错误 | 群友可以确认爸爸的任务 |
| 集成缺陷 | 模块各自正常，组合后失败 | QQ 群消息能回复，但动作没有执行 |
| 数据缺陷 | 记忆、任务、回执不一致或污染 | 群聊内容进入私人长期记忆 |
| 稳定性缺陷 | 重启、断线、超时、重复执行后异常 | 外部操作处于未知状态时自动重试 |
| 安全/隐私缺陷 | 凭证、权限、上下文或外部发送边界错误 | 未绑定身份可以触发外部操作 |
| 文档缺陷 | 文档描述与生产代码或实际验收不一致 | FEATURES 写已实现，实际只有脚本原型 |
| 可观测性缺陷 | 发生问题但无法查询证据 | 没有 task_id、截图、平台对象 ID |

## 3. 统一缺陷生命周期

所有问题都必须遵循：

```text
reported
  → triaged
  → reproducible
  → root_cause_found
  → fix_in_progress
  → fixed
  → regression_verified
  → real_device_verified
  → observation
  → closed
```

特殊状态：

```text
duplicate · rejected · blocked · mitigated · reopened
```

`fixed` 只表示代码修改完成；`closed` 必须同时满足自动测试、真实路径验收和观察窗口要求。

### 缺陷单最低字段

```yaml
id: BUG-YYYYMMDD-xxxx
title: 简短、可检索的现象
severity: S0|S1|S2|S3
category: logic|state|integration|stability|security|docs
source: desktop|wechat|qq|android|douyin|voice|life
reporter: user|test|log|monitor
first_seen_at: ISO-8601
last_seen_at: ISO-8601
environment: Mac model, macOS, Node, phone, app versions
preconditions: []
steps_to_reproduce: []
expected: 预期行为
actual: 实际行为
evidence: message_id/task_id/screenshot/log/test
suspected_root_cause: 初步判断
fix: 修改的代码、迁移或配置
regression_test: 测试名称或文件
real_device_check: 实机验收步骤
observation_window: 例如 24h/7d/20次
closure_evidence: 关闭证据
```

## 4. 严重级别和响应目标

| 级别 | 定义 | 处理目标 |
| --- | --- | --- |
| S0 | 凭证泄露、未授权外发、重复发布/付款、数据损坏 | 立即停用相关适配器，先保护数据，再修复 |
| S1 | 核心通信不可用、动作状态与真实结果相反、群友可触发主人权限 | 24 小时内定位，修复前关闭风险动作 |
| S2 | 单一渠道失败、语音听感异常、任务不能恢复、桌面状态错误 | 纳入当前迭代，完成自动和实机回归 |
| S3 | 文案、视觉、日志、非关键体验问题 | 排期修复，不阻断核心服务 |

## 5. 当前缺陷基线

### S1：多个大脑，没有统一核心

桌面、微信 iLink、QQ、电话各自拥有系统提示词、能力清单和上下文。结果是同一件事在不同渠道得到不同判断，记忆和人格也可能不一致。

修复方向：建立统一 Core 接口，渠道只负责收发消息；统一输出 `reply + intent + task_proposal + memory_events`，禁止渠道自行定义外部能力。

### S1：动作协议不统一

旧的 `[DO:...]` 文本标记与新的 `external_tasks` 并存。模型可以说“好，我马上去做”，但没有动作标记，造成口头承诺与执行状态分离。

修复方向：所有外部动作统一走任务 API；模型不再直接决定执行；自然语言只负责提出意图，系统负责创建、确认和执行任务。

### S1：群聊权限边界不足

群聊中不应由任意群友批准爸爸的抖音、电话、发布等动作。当前需要绑定 `proposer_peer_id`、`approver_peer_id`、账号和任务过期时间。

修复方向：群聊外部动作默认关闭；只有爸爸私聊发起或爸爸身份明确确认才允许执行；群友只能看到“等待主人确认”。

### S1：外部动作缺少真实回执

动作成功不能由模型语言决定。必须保存平台对象 ID、设备回执、截图、控件文本、时间和执行步骤。

修复方向：每一步执行器返回结构化 `receipt`；无回执只能是 `unknown`，不能写入“完成”记忆。

### S1：任务中断与重复执行风险

任务目前需要补充 `running`、`unknown`、`cancelled`、`expired`，以及进程崩溃后的恢复策略。外部操作在结果未知时不能自动重试。

修复方向：每个动作使用幂等键；重启先查询平台/设备实际状态，再决定继续、取消或人工核对。

### S1：记忆系统和渠道状态分裂

桌面、QQ、微信、日记和动作记录没有完全统一的来源、隐私范围和删除传播规则。

修复方向：统一记忆事件接口，明确 `channel`、`peer_id`、`source`、`confidence`、`privacy_scope`、`revision_of`；群聊默认不进入爸爸私有长期记忆。

### S2：语音生产配置混乱

Tingting、Qwen、Vivian、MiniMax、多音色混合曾先后出现，文档与生产配置可能不同步；音频桥还可能引入回声。

修复方向：生产只保留一个明确音色和版本；关闭音色混合；记录 provider、voice_id、speed、pitch；为普通语音和实时通话使用独立音频路径；增加单声道、重复播放和回声检查。

### S2：抖音能力矩阵不真实

读取互动、回复评论、点赞、发布、收藏、互动守护的实现程度不同。点赞目前没有稳定适配器，不能列为已实现。

修复方向：每个平台、每个动作维护 `implemented / tested / real_verified / disabled` 状态；未实现能力不得进入模型可用能力提示。

### S2：Android/ADB 自动化缺少长期验收

ADB、坐标和 UI 树脚本容易受到分辨率、MagicOS、App 更新、锁屏和 UI 改版影响。一次点击成功不能代表稳定能力。

修复方向：每个操作保存请求、截图、控件定位、实际回执；连续执行 50 次样例，记录断线、锁屏、超时和恢复结果；遇到不确定状态立即停止，不猜成功。

### S2：文档与生产代码不一致

`FEATURES.md`、`README.md`、路线图和语音文档对生产音色、测试数量、手机能力和社交能力的描述已经出现差异。

修复方向：改为唯一能力状态矩阵，每项只允许五种状态：`未实现 / 原型 / 自动测试 / 实机通过 / 稳定运行`。每次发布必须同步文档和版本号。

## 6. 目标架构

```text
Channel Adapter
  ↓ normalize message
DaFeiYu Core
  ├─ Identity / Persona
  ├─ Memory Service
  ├─ Intent Parser
  ├─ Policy Engine
  ├─ Task Orchestrator
  └─ Receipt Service
  ↓
Platform Adapters
  ├─ Desktop
  ├─ Android/ADB
  ├─ WeChat
  ├─ QQ
  └─ Douyin
```

模型只能返回结构化提议：

```json
{
  "reply": "爸爸，我识别到回复评论和点赞两个动作。要执行吗？",
  "intent": "douyin.manage_comments",
  "task_proposal": {
    "operations": ["reply_comments", "like_comments"],
    "target": "my_latest_work",
    "requires_confirmation": true
  }
}
```

模型不得直接返回“已完成”。“已完成”必须由 Receipt Service 根据真实执行器回执生成。

## 7. 分阶段修改计划

### Phase 0：冻结风险面（1 天）

- 群聊关闭抖音、电话、发布、点赞等外部动作。
- 保留文字、天气和普通问答。
- 原生微信语音气泡保持关闭。
- 固定当前单一生产语音配置。
- 记录当前数据库和配置备份。

验收：高风险动作不会被群聊触发；服务重启后状态不变。

### Phase 1：统一任务与权限（3–5 天）

- 扩充 `external_tasks` 字段：来源、提议人、确认人、动作、账号、过期时间、尝试次数、幂等键、证据。
- 加入 `running/unknown/cancelled/expired`。
- 增加任务查询、确认、取消、重试 API。
- 删除外部动作对 `[DO:...]` 的依赖。
- 爸爸身份确认绑定到账号和 peer。

验收：任务可查询、可取消、可恢复；群友不能批准爸爸任务。

当前进度：基础任务字段、幂等键、过期回收、任务详情/列表/取消 API 已加入；QQ 群确认已禁止，只有标记为“爸爸”的私聊可批准；进程启动时 `approved/running` 会转为 `unknown`，避免重启后盲目重做。仍需补真正的恢复 worker 和操作级平台回执。

2026-11-14 执行结果：任务查询命令 `npm run tasks` 可用，当前没有待处理任务；Magic5 重启后短暂离线并自动恢复在线；全套自动测试 63 项通过。

2026-11-14 继续执行：任务迁移增加 `running/unknown` 中断恢复、审批人、过期时间、幂等键、尝试次数和证据字段；新增任务详情/取消命令。QQ 群消息不再写入爸爸的私人长期记忆，新增回归测试。当前自动测试总数更新为 64 项以上，完整结果以最新 `runtime/build-tools/tests-all-phases-current.log` 为准。

### Phase 2：统一回执和审计（3–5 天）

- 所有执行器返回统一 receipt。
- 保存截图、平台对象 ID、设备命令 ID、时间和错误码。
- 桌宠活动引用 task_id，不再只显示泛化“开心/完成”。
- 无回执统一显示“结果未知”。

验收：每个外部动作可以根据 task_id 回查全过程。

### Phase 3：统一人格和记忆（5–7 天）

- 统一桌面、微信、QQ、电话的 Core 请求格式。
- 统一记忆服务和隐私范围。
- 群聊默认不写私人记忆。
- 动作回执才可写入经历。
- 删除和修订传播到所有渠道上下文。

验收：跨渠道召回一致；群友内容不会污染爸爸记忆；删除后不再召回。

### Phase 4：平台能力收敛（1–2 周）

- 抖音先只保留“读取互动”和“回复评论”两个能力。
- 点赞单独实现和验收，不复用回复逻辑。
- 发布、点赞、评论全部加入审批和幂等。
- 小红书、哔哩哔哩保持未实现，不加入模型能力提示。

验收：每个动作连续 20 次实机测试，结果、截图和平台对象 ID 可回查。

### Phase 5：稳定性观察（7 天）

- 连续运行 7 天。
- 每天记录服务重启、消息延迟、失败率、未知任务、语音耗时、Android 在线率。
- 至少演练一次 Connect 重启、桌宠重启、手机断线、模型超时和数据库恢复。

验收：没有重复外发、未授权动作、假成功、任务丢失和记忆污染。

## 8. 每次修复必须回答的问题

修复提交和最终报告必须回答：

1. 用户看到的具体问题是什么？
2. 能否稳定复现？复现条件是什么？
3. 根因在模型、状态机、权限、适配器还是设备？
4. 修改了哪个状态转换或数据契约？
5. 是否增加了回归测试？
6. 是否做了真实设备或真实平台验证？
7. 如果结果未知，系统如何避免重复执行？
8. 运行观察窗口多长？指标是什么？
9. 文档、能力矩阵和版本号是否同步？

## 9. 发布门槛

任何新外部能力满足以下条件前，不得标为“已实现”：

- 有确定的权限和确认规则；
- 有唯一 task_id 和幂等键；
- 有执行中、失败、未知和取消状态；
- 有真实平台或设备回执；
- 有自动回归测试；
- 有至少一次真实端到端验收；
- 有重启、断线和超时处理；
- 没有把密钥、隐私内容写入日志；
- 文档能力矩阵已更新；
- 观察窗口结束后才关闭缺陷。

## 10. 当前最重要的工作顺序

```text
先冻结群聊外部动作
→ 统一任务和权限
→ 统一回执和审计
→ 统一记忆与人格入口
→ 收敛抖音能力
→ 修正语音生产配置
→ 完成 7 天稳定性观察
→ 再扩展平台和自主能力
```

在这些步骤完成前，不继续扩展购物、短信、电话自动化、多个社交平台同时运营或“自我成长”功能。稳定性优先于能力数量。

发布门槛检查命令为 `npm run release:check`，会验证文档、任务与观察入口、Magic5 在线状态、没有运行中/已批准的未知任务、运行目录隔离和已跟踪文件的密钥模式。它不能替代真实平台回执或 7 天观察。

观察汇总命令为 `npm run stability:summary`，输出样本数、覆盖小时、设备在线采样率、任务异常、未知/失败命令和 `seven_day_ready`。手动和 Connect 自动采样现在写入同一文件格式。只有 `seven_day_ready=true` 并且异常项经过复盘，才能关闭稳定性观察阶段。

当前 release check 会在 Magic5 离线、存在未决的运行中任务、存在 unknown/dispatched 设备命令、稳定观察未覆盖 7 天、能力文档缺失或跟踪文件出现明显密钥模式时失败，阻止稳定版发布判断。

任务执行结果现在通过 `connect/receipts.mjs` 归一化为 `succeeded / failed / unknown`，包含 adapter、operation、观察时间和 evidence。未知结果不会写成成功；平台截图和对象 ID 仍需由各适配器逐步提供。
